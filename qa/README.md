# QA layer of the `olx-br` fork

This folder is the QA layer of the package. It has three gates and one source of truth.

| file | what it is |
|------|------------|
| `assertions.json` | **the source of truth of the QA.** The 26 assertions (`A01`..`A26`) measured against the real OLX API on 2026-10-20, with the status and the body that each call has to answer. The live suite reads this file and nothing else. |
| `contract.test.js` | the **offline contract suite** (`node:test`). Deterministic, no network, no secret. It locks down the public surface, the verb, the path, the body and the authentication of every public method, and the whole error contract (`OlxApiError`). |
| `live.test.js` | the **live suite** (`node:test`). It replays the 26 assertions of `assertions.json` against `apps.olx.com.br` and `auth.olx.com.br`. It is off by default and it is never a merge blocker. |
| `compat-check.js` | the **compatibility gate**. It compares the build of the branch (`dist/`) with the frozen `olx-br@1.0.6` of `baseline/` and prints `RESULT: COMPATIBLE (COMPATIVEL)` or `RESULT: INCOMPATIBLE (INCOMPATIVEL)`. |
| `baseline/` | the **frozen comparison base**: the `dist` of the package published on npm as `olx-br@1.0.6`, **MIT licensed, author Vinícius Rossmann Nunes**. It is a copy of the published tarball (`https://registry.npmjs.org/olx-br/-/olx-br-1.0.6.tgz`), kept byte identical (the sha256 of every file is in `baseline/manifest.json` and the gate verifies it). It is never regenerated by accident and it never talks to the API. |
| `baseline/manifest.json` | the manifest of the frozen baseline: the origin of the tarball, the list of the files and their sha256. |
| `gen-baseline.mjs` | regenerates `baseline/` from an extracted tarball of the published package: `node qa/gen-baseline.mjs <extracted folder> qa/baseline`. Only on purpose. |
| `contract-matrix.json` | the contract matrix of the Dev team (the method, the path, the authentication and the live answer of every public method). It is the source of truth of the unit suite of `test/`. |
| `consumer/` | the consumer of the package used by the compatibility test of `test/qa/` (the published 1.0.6 and the current build). |
| `ci.yml` | the **proposal** of the QA jobs for `.github/workflows/ci.yml`. This file is not read by GitHub: the workflow lives in `.github/workflows/`. |
| `run-contract.cmd` | the Windows runner of the offline contract suite. |
| `run-live.cmd` | the Windows runner of the live suite. |
| `package.scripts.proposto.js` | the **proposal** of the npm scripts of the QA layer. The `package.json` of the fork is not touched by this branch. |

## The two QA layers of the package

The package has two QA layers and they do not replace each other:

* the **gate of the Dev team**, in `test/qa/` and `test/integration/`, written in vitest and
  driven by `qa/contract-matrix.json`. Its scripts are `qa:contract`, `qa:compat` and
  `qa:live`;
* the **QA layer of this folder**, written in `node:test` and driven by
  `qa/assertions.json`. It runs against the **built** package (`dist/`), it needs no new
  dependency and the live suite runs alone, on the machine of the owner, without the tool
  chain. Its scripts, if the team wants them, are `qa:matrix:contract`,
  `qa:matrix:compat` and `qa:matrix:live` (see `package.scripts.proposto.js`).

They are complementary: the gate of the Dev team is part of `npm test` and therefore of the
required CI, and this layer is the executable form of the measurements of the QA matrix
(`A01`..`A26`), the one that `docs/CONTRACT.md` cites.

## The exact commands

Everything is run from the root of the package, and everything needs the dependencies of
the package (`npm ci`) and the build (`npm run build`), because the QA runs against `dist/`.

### The offline gate (required, deterministic, no network)

```
npm run build
node --test --test-reporter=spec qa/contract.test.js
node qa/compat-check.js
```

On Windows: `qa\run-contract.cmd` (the contract suite) and `node qa\compat-check.js` (the
gate). Both have to exit with `0`.

### The live suite (optional, never a merge blocker)

```
set OLX_LIVE=1
node --test --test-reporter=spec qa/live.test.js
```

On Windows: `qa\run-live.cmd`.

Environment:

| variable | effect |
|----------|--------|
| `OLX_LIVE=1` | turns the live suite on. Without it every test that talks to the network is **skipped**. |
| `OLX_ACCESS_TOKEN` | the real token. **Optional**: without it the suite runs with a **fake** token and only exercises the authentication and the shape of the error, never a real permission. |
| `OLX_FAIL_ON_LIVE=1` | a network failure becomes a **FAIL** instead of a **SKIP**. Off by default, so that an unreachable API never breaks a local run. |

## The rules of the live suite

1. **The live suite is never a merge blocker.** It talks to the real API, it may be
   unreachable from the runner and the answers of the OLX change without notice. The
   required gates are the offline contract suite and the compatibility gate. In the
   proposed workflow (`ci.yml`) the live job has `continue-on-error: true`.
2. **`www.olx.com.br` is forbidden.** It answers `403` (Cloudflare) and it is not part of
   the contract of the API. A test against it is a false negative, not a defect of the
   package. The matrix is checked against this rule on every run, and the hosts of the
   matrix are only `apps.olx.com.br` and `auth.olx.com.br`.
3. **No secret, ever.** Without `OLX_ACCESS_TOKEN` the suite runs with a fake token.
4. **A network failure is a SKIP, not a FAIL** (unless `OLX_FAIL_ON_LIVE=1`).
5. **The matrix is the source of truth.** A row of `assertions.json` that answers
   differently from the measured value is a change of the API, not a change of the
   expectation: the row has to be re-measured and the observation updated.
6. Three rows are **accepted as unstable** and are never a contract: `A06` (the token of
   the `autoupload` group in the header answers `400` or `500`), `A21` (the lead of the
   `autoservice` group answers `401` or a truncated `500`) and `A26` (the root of
   `apps.olx.com.br` answers `403` or `404`). They exist to prove where the token goes,
   not to freeze a status.

## The compatibility gate

`compat-check.js` compares the build of the branch with the frozen `olx-br@1.0.6` of
`baseline/`, twice:

* the **declared surface** (`dist/index.d.ts` against `baseline/dist/index.d.ts`): a
  method that is removed, or whose signature changed without being declared, is
  `INCOMPATIBLE`;
* the **runtime surface** (the two builds loaded): a member that is removed, or whose
  arity changed, is `INCOMPATIBLE`.

The version `2.0.0` declares two breaking changes, and the gate lists them on every run:
the rejection value is now always an `OlxApiError` (1.0.6 rejected with the raw body),
and the authorization URL lost the double slash (`//oauth` became `/oauth`, both answer
`302`, the matrix `A25`). Everything else that the fork adds is additive: `Olx.OlxApiError`,
`Olx.SCOPES` and the three chat methods.

## Nothing is published

The package is `private: true` and nothing of this folder is published: the `files` of
the `package.json` is `["dist"]`. The QA layer never talks to the npm registry, and the
only network it uses is the API of the OLX, in the live suite.
